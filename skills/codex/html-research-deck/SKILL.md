# HTML research deck

This skill owns the production step only: the engine, the visual system and the QA of an HTML deck. The argument comes first and is governed by `research-talk`: storyline table with one message per slide, slide language asked explicitly, user approval recorded, `storyline.json`, citation mapping and the fact-check gate before delivery. Read `research-talk/references/workflow.md` and `storyline-format.md` when a talk starts; when the user hands over an already approved flow, build from it without re-asking.

## Workflow

1. **Scaffold** in the project's artifact location (`inbox/<talk>-deck/` or the project's slide folder), never inside this skill:
   `python3 scripts/new_deck.py /abs/<talk>-deck --title "…" --lang ko --slides title,figure,figure-render,closing`
   This copies the engine (`css/`, `js/`, `vendor/` with Pretendard and KaTeX) and writes `index.html` with the shape sprite inlined and the chosen fragments from `assets/deck/templates/` in order. Keep one slide per `<section class="slide">`; keep every sentence of the source in `<aside class="notes">`.
2. **Taste benchmark before the rest.** Build two or three representative slides first, including one mechanism scene, run the QA below, publish, and stop for the user's verdict. Only after the verdict build the remaining slides to that standard. This is how the reference deck was accepted (user decisions below).
3. **If you are a GPT model (Astra, Sol, Terra and so on), read `references/builder-notes-gpt.md` before drawing and follow it:** you copy worked slides from `scripts/kit_gallery.py` and draw with `scripts/scene_kit.py`, and `scripts/style_gap.py` measures how far the result is from the accepted decks. Claude models skip this step.
4. **Per slide**, read `references/design-system.md` once per thread and then: write the one message; decide what the single picture must show (actors, states, the change, in 2–3 cells); choose a layout fragment; draw the scene with the sprite shapes (`<use href="#shBlob">` etc.) and the scene grammar; put the source sentences and figure provenance in the notes. Structural evidence (PDB renders) follows `research-talk/references/molecular-visualization.md`; a render sits in its own panel with leader labels, never as a decorative background.
5. **Render loop is yours, not the user's.** After each slide: `scripts/check_layout.py` (measured boxes: text outside its panel, label collisions, rim crossings, empty bands) and `scripts/shots.sh`, open the full-resolution PNG, fix overlaps and clipped labels, render again. A slide is "drawn" only after both pass: zero layout errors, no underfilled or unbalanced panel, and one full-size inspection with no finding. The first draft already follows the rules; the loop catches geometry, not taste.
6. **QA and delivery** per `references/qa.md`: `scripts/check_deck.py` (grid, closing line, citation markers, Korean endings, text sizes), `scripts/check_layout.py` (rendered measurement), all-slide PNGs plus the contact sheet, `scripts/export_pdf.sh`, publish through the host's HTML preview workflow (host-context), verify served bytes, assets and the PDF, then report what was verified and what was not. Deliver the HTTPS link first, the local link, the PDF path and the folder on the host where it exists.
7. **Revisions** edit the slide in place; re-run `check_deck.py` and the shots for the touched slides; never regenerate the deck from an older spec over user edits. The publisher never overwrites a slug: publish `-v2`, `-v3`, … and say which is current.
8. **Obsidian archive** follows `research-talk/references/workflow.md`: save the PDF and Markdown script in `Slides/` with date/title names, preserve the existing script length, and connect them through the presentation note. HTML preview slugs may retain internal version labels; archived filenames do not. When asked to export existing `<aside class="notes">` content, preserve every slide's notes in order without expanding the script.

## Design system (summary; details in `references/design-system.md`)

- Stage 1920×1080; title block starts at x 130 and ends at y 152; panels from y 176 to 898; every gutter 24 px; panel padding 20 px, so what a panel holds starts at x 130 under the title; the closing line is a white card at x 130–1790, y 922–1000; cite at the bottom, 17 px.
- Stage first (2026-11-02): key figures sit directly on the warm stage and panels are transparent. White is a card that holds one thing: one formula, one chart among several, the closing line. Panels in one row share a height. No coloured bars, blurred washes, gradient text, letter-spaced labels, icons or animation.
- Context-dependent academic terms stay in English in Latin script, on labels as well (`message-style.md` rule 4). Text budget: title (noun phrase), labels on the drawing, one closing line; sentences go to the notes. Type scale: 24 px is the base; body lines and figure labels 22–24 px, lane headers 24, emphasis 26–28, chart value labels 24–26, names 24–30; under 22 px only for muted reference notes or one dense 30-row chart (19 px) (type scale in `references/design-system.md`).
- Scene grammar: organic protein blobs with soft shading, capsule = small molecule, beads = ubiquitin, barrel = proteasome, cell with nucleus and DNA; the same actor keeps its shape across states; dashed outline = absent, red × = blocked, red dot = mutation; grays for machinery, one blue for the drug or path of interest, amber for the substrate, red only for a key phrase. Mechanism slides show the biological consequence (e.g. transcription → growth) as a cell-level panel, not only the molecular steps.
- Korean copy on slides is noun phrases (`research-talk/references/korean-slide-copy.md`); citations `[n]` at the point of use and resolved in the cite line; every number and claim traces to a source in the notes.
- Taste standard: the accepted three-slide sample `taste-sample-20261030-v4` (Mac mini `inbox/html-deck-conversion-20261030/out/taste-sample/`); compare new work against it.
- The closing slide's question panel is the user's slot (`owner: user` in `storyline.json`): generate only a content header and two or three questions, never a header such as "발표자 생각", and goal-loop builders leave that slide alone.
- A deck with a cover figure places `kit.hero_bridge` on a transparent panel (gallery slide 1).
- In `.fx` and `tex()` strings write `<` and `>` as `&lt;` and `&gt;` only when the string is not escaped again (a card path escapes once); otherwise KaTeX receives `&` and the formula shows a raw entity, which `check_layout.py` reports as `tex-unrendered`.

## Hosts

- Rendering needs Chrome (`CHROME` env; default `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`). No npm, no Python packages.
- Publishing: the Mac mini `html-preview` publisher (path and URL form in `~/.codex/host-context.md`) prints the MacBook HTTPS link first, then the Mac mini local link; verify both routes as in `references/qa.md`. On a host without a publisher, deliver the deck folder and the PDF and say so.
- The engine copy in `assets/deck/` is canonical; the inbox starter `html-deck-starter-20261030` on the Mac mini holds the development history and the example decks.

## Message goal (copy register) — after the design goal

`scripts/deck_copy.py` dumps the visible copy; `scripts/copy_lint.py` counts the rule slips a builder can fix before the judges run (banned closing-line words, case numbers without scope words, author marks in lanes or labels, comma rhythm, hand-off candidates, comma-split titles; advisory, also run by `iterate_message.py` into `deck/qa/copy-lint.txt`); `scripts/score_message.py` measures it against `rubric-message.md` (M1–M7) and merges the independent judge; `scripts/judge_message.py` runs the judge on the copy dump, the paper context and the contact sheet only; `scripts/iterate_message.py` is one iteration (builder with `references/builder-brief-message.md` → checks → shots → fresh design judge → message judge → `iter-msg-<n>.json`, with the storyline's titles and closing lines re-snapshotted into `work/storyline.json` while `work/storyline-v1.json` keeps the approved ids/roles/evidence); `scripts/goal_loop.py --iterate iterate_message.py --prefix iter-msg` runs it unattended. Only `references/builder-brief-message.md` is embedded in the builder prompt (procedure + consolidated rules + current priorities); the per-iteration judge findings the rules were distilled from live in `references/builder-brief-message-history.md` — when a finding recurs, change the rule, do not append another prescription (iterations 4–6 plateaued at 38.67/38.67/38.22 of 50 while prescriptions accumulated and contradicted each other). Before attributing a score change to the deck, measure judge-to-judge variance with `scripts/judge_compare.py` on a replicate run over the *same* copy dump (`judge_message.py --out <deck>/deck/qa/replicates/…`): on the CausalGame deck two Opus 5.5 max runs on identical text scored 37.22 and 34.56 of 50 and placed the N5 deductions on different slides, so a single-judge pass within ~3 points of the threshold is not evidence of a better deck — report a pass together with a replicate, or score with the median of three judges. `iterate_message.py --judges 3` (and `goal_loop.py --judges 3`) runs three concurrent judge draws on the same dump and scores their per-item median via `scripts/judge_median.py` (judge-file shape preserved; rubric, weights and threshold unchanged; default stays 1 draw). On the CausalGame deck the single-draw loop reached 92.22 at iteration 11 while a replicate on the same dump scored 88.89 — three replicates in a row differed by exactly one N5 deduction — so for the next deck start the loop with `--judges 3` and treat a single-draw pass near the threshold as provisional until the user has reviewed it. Freeze with `score_message.py … --freeze deck/qa/rubric-message-frozen.json` before the first iteration; the paper context for the judge lives at `<deck>/paper/context-for-judge.txt` (abstract verbatim + scope note).
- "이건 지금 이번에 한거처럼 규칙을 정해두면 요청하는거 그대로 만들 수 있는거아닌가?" and "좋은거같애. 1 2b 가 좋을듯?" → the rules live here so a request yields the deck directly; the taste benchmark of 2–3 slides stays as the one user checkpoint before the full build.
- Read `references/message-style.md` before writing visible copy (kickers, titles, lane headers, labels, closing lines, cite lines); a title must carry the slide's point.
- Count copy length by width: in the title limit (34), the kicker limits (section at most 14, subtopic at most 24) and the closing-line limit (12 to 48), a Latin letter or digit counts as 0.6 of a Hangul glyph, because English is narrower at the same size (rubric-message M1 to M3).
- A deck passes the goal when the message score and the design score are each at least 90, both scored by fresh judges.
- Visible copy (kickers, titles, lane headers, labels, body text, closing lines) contains none of the tokens `저자`, `발표자`, `모식`, `번역`; attribution and caveats go in the cite line (rubric-message M10).
- Use one written form per quantity across the deck, taken from the `glossary` in the storyline (a `use` form and `avoid` forms per quantity; the caller owns it); rubric-message M4(b) counts the `avoid` forms.
- A slide with `owner: user` is still read by the message judge. When the judge evidence names such a slide, the caller fixes the factual wording, records before and after, and runs `score_message.py` as well as `check_layout.py`.
- A design pass near 90 on one judge draw gets two replicate draws before it is reported.


## Builders on other CLIs, and the equivalence test (2026-11-01)

`scripts/agent_cli.py` runs a builder or a judge on `claude -p` (models `claude-*`) or `codex exec` (`gpt-6-astra`, `gpt-6.1-sol`, …; effort through `-c model_reasoning_effort`). `iterate_deck.py`, `iterate_message.py`, `goal_loop.py` and `goal_chain.py` take `--model/--effort` for the builder and `--judge-model/--judge-effort` for the judges — keep the judge fixed (Opus 5.5 max) when builders differ, or the scores are not comparable. Judges are isolated from the user's own instructions: Claude with `--setting-sources '' --strict-mcp-config`, Codex with a minimal `CODEX_HOME` (`~/.codex-judge-home`: auth link + the bridge base-URL line; with the normal home a probe answered that it had read the shared working agreement and carried 28k input tokens, with the minimal home not, 14k). Codex builders run `-s danger-full-access` because headless Chrome aborts inside the `workspace-write` seatbelt sandbox (check_layout "no DOM dump", shots.sh "Abort trap: 6", 2026-11-01) — the same trust the Claude builder has with acceptEdits + Bash; builders keep the user's normal environment on purpose, because that is what the user's own sessions look like. Codex's `--json` event stream carries usage tokens but no model field, so a Codex run's record is the requested model plus the CLI version (`agent_cli.run` returns `model_reported` only for Claude).

`scripts/equiv_run.py ROOT --paper … --storyline … --builders claude-opus-5-5:max,gpt-6-astra:high,gpt-6.1-sol:xhigh --judges 3 --codex-parallel` is the equivalence test the user asked for ("나는 gpt 모델 (astra or sol high) 도 자주 쓰는데, 각각을 high, xhigh로 했을 때 비슷한 결과가 나오도록 하면 좋겟음"): every builder gets the same `references/builder-brief-fresh.md`, the same paper folder and the same approved storyline (`work/storyline-v1.json`, with `glossary` and `owner`), builds in its own folder, is measured by the same scripts and scored by the same judge (median of three draws — `judge_median.py` handles both judge-file shapes), and `summary.md` shows each builder's gap to the first builder in the list; "비슷하다" = within ±3 on both design and message. When a builder falls outside, move the item it lost into a script check or a brief rule rather than into model-specific prose — the rules that already live in scripts (`check_layout.py`, `score_*.py`, `density.py`, `deck_copy.py`) are the portable part. `scripts/goal_chain.py DECK --judges 3 --cost-cap-usd …` runs the judge-only baseline, the design loop and the message loop in order and stops at the cap.

First result (2026-11-01, Latent SI, one build per builder, judge median of three, design / message): Opus 5.5 max 85.44 / 81.56, Astra high 80.0 / 80.0, Sol xhigh 79.89 / 80.44 — message within ±3, design outside, and nearly all of the design gap is H on the method slides (H summed over slides 2–12, out of 22: 16 / 4 / 5; over slides 13–19, out of 14: 8 / 7 / 7). Arrow counts, box-only scenes and rendered ink did not explain H within a builder (ink stayed at 0.19 while H rose from 7.78 to 12.83 across the Claude loop), so none of them became a rule; a judge-fed loop on the GPT decks came next (Mac mini: `inbox/latent-si-equiv-20261101/gap-analysis/README.md`).

Second result (2026-11-02, same paper and judge, design / message): with `builder-notes-gpt.md`, `scene_helpers.py` and the new `density.py` the first builds were Astra 80.33 / 75.34 and Sol 80.66 / 74.12, so the notes alone did not raise the total (method-slide H rose, layout I and message fell). Six judge-fed iterations (three design, three message) then reached Astra 88.01 / 83.67 and Sol 85.00 / 86.56, against the accepted v10 at 90.00 / 91.12 and the Opus first build at 85.44 / 81.56. On a GPT builder, budget for the loop rather than expecting the first build to carry it: `goal_chain.py DECK --skip-baseline --model gpt-6-astra --effort high --judges 3 --cost-cap-usd …`. Not measured: a Claude first build through the same six iterations, a GPT loop without the notes, Astra xhigh, Sol high, another paper (Mac mini: `inbox/latent-si-equiv-gpt-notes-20261101/README.md`).

Third result (2026-11-02, same paper, kit and gallery with stage first and English terms, storyline with v11's titles, judge median of three, rubric reworded): first builds Astra high 82.50 / 80.44 and Sol xhigh 81.88 / 80.67, against 80.33 / 75.34 and 80.66 / 74.12 with the rule-only notes. The accepted deck after its own loops is v13, 89.17 / 90.44. The look now matches by eye and by `style_gap` (0 findings on both); what still separates them is the judge's H on mechanisms: arrows that start or end in empty space, the same blue box used for models, formula steps and loss terms, a step the slide talks about that is not drawn. Same paper, so this says nothing about other papers; the kit came from this deck's Opus code.

Fourth result (2026-11-02, a paper the kit did not come from, each model wrote its own storyline, judge Opus 5.5 max): Opus 5 76.27 / 96.67, Sonnet 5.5 85.84 (one usable draw) / 97.22, Astra high 80.66 / 94.33, Sol xhigh 81.38 / 85.78. The Opus 5.5 build was stopped by the safety classifier and not retried, and 4 of 24 judge draws were blocked, so a paper near biology or chemistry cannot give an Opus 5.5 baseline. What the judges held against the GPT decks went into the notes, gallery slides 15 and 16 and `style_gap.py`; not re-measured yet.

Fifth result (2026-11-02, Latent SI, judge median of three): after four design and five message iterations Astra high 89.61 / 90.00 and Sol xhigh 88.55 / 91.44, against the Opus deck v17 90.06 / 90.45, so both within ±3. Not a first-build comparison, and the kit came from this paper's Opus deck. Layout now measures like the reference deck: largest white box 6.2% against 6.1%, occupied share 25-26% against 25.2%. Design fell while the message iterations ran (Sol 90.72 to 88.55); cause not established, judge spread is 1-2 points.

Sixth result (2026-11-03, the DDSBM paper again, GPT first builds with the graph rules, no Opus 5.5 judge): the stock pentagon is gone from both, node-link figures are on two slides at 44 px and 3.4 px, paper crops on 2 slides (Astra) and 1 (Sol), and `style_gap.py` is clean on both. An Opus 5 reader put them at 7/10 and 8/10 against the accepted decks, one read, not a calibrated score. A first round with a broader crop rule had pasted crops on 8 and 11 slides; a rule that points at one tool gets overused unless it says where the tool stops and a check counts it. Helpers and gallery came from this paper's Claude decks, so this is not a generalization test.

Seventh result (2026-11-03, the same DDSBM GPT decks, kit only, no model run): a paper drawing stored as a 220 ppi bitmap went soft twice. Poppler smeared its edges even at the bitmap's own ppi (median edge 3 px against 1 px in the bitmap), and the browser smeared them again when 986 px were shown at 700-960 px. `paper_crop` now copies the bitmap's own pixels, falling back to the rendered page when the crop spills off the bitmap or the page draws over it, and `w=None` with `pad` places them 1:1. Four decks re-rendered this way measure like Sonnet 5.5's 1:1 figure: median edge 1.0 px, mean 2.04-2.11 px against 2.06, midtone share 75.9-77.9% against 76.3%. The Claude decks rebuild byte-identical; they do not call `paper_crop`. A fresh GPT build has not been run with this note yet.

Where Opus 5.5 is stopped by the safety classifier, Sonnet 5.5 is the Claude baseline; no separate paper is run for an Opus 5.5 baseline.

## Maintenance

A new shape that will recur goes into `assets/deck/sprite-research.svg`; an accepted style correction becomes a `check_deck.py` rule or a line in `references/qa.md` in the same turn; an entry in User decisions is never dropped or narrowed without asking. Validate with the system skill-creator's `quick_validate.py` (`uv run --with pyyaml`).
