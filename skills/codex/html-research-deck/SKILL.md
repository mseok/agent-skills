# Research deck: storyline first, then an HTML deck

Work with the researcher on the argument before making slides. Read the relevant experiment context yourself; the user should not have to reformat notes into slide-ready material. This skill holds both halves of a talk: the storyline with its approval and gates, and the production of the deck (the former `research-talk` skill was merged into this one on 2026-11-12). The product is a static HTML deck; an editable PPTX is a second route, taken only on request. The HTML deck has two layouts with the same fonts: the research theme, which is the default, and Folio, used when the user asks for it by name (`references/folio.md`).

## Routes

| the user asks for | do |
|---|---|
| a new talk (발표자료, 슬라이드, a deck, "HTML 덱") | Storyline → approval → Build the HTML deck |
| a deck from an already approved flow or brief | build from it without re-asking (Brief-driven runs) |
| "same as before" (이전과 같이) | the earlier approved flow from the presentation note; read it and proceed unless the user changes it |
| the Folio layout ("Folio", "Folio 양식", "난과 판 양식") | the same storyline, gates and QA; grid, kit and checks from `references/folio.md` |
| a change to an existing deck | Revisions |
| PPTX, PowerPoint or Keynote output, or an edit of an existing PPTX | the storyline and gates here, production by `references/pptx-production.md` |

The storyline, the approval step and the gates apply in every harness and on every host (Codex desktop, Claude Code, the lab server); only the production step differs. If a tool the route needs is unreachable in the current harness, say so once and build with what is reachable; never skip the approval step because a tool is missing.

## Storyline (develop or resume)

1. Read `references/workflow.md`. Use only `obsidian_main` for Vault access. Search for an existing presentation preparation note before creating one. Read its current SHA, approved flow, unresolved issues, evidence links and latest edited deck location.
2. Take the user's topic and overall context as the starting point. Recover question reports with `investigation_context`, then read relevant experiments and linked evidence. Narrow retrieval to the presentation question. Do not infer that the newest experiment replaces all earlier evidence.
3. Establish audience, purpose, time and slide language. The product is an HTML deck unless the user asks for PPTX, PowerPoint or Keynote; do not ask about the format. For each new talk, explicitly ask whether slides should be Korean or English unless the user has already specified the language for that talk; never infer it from the chat language or a previous talk. On resume, honor the user's recorded choice without asking again. Record that choice and its user reference in the brief/preparation note before approval. Ask concise questions for other consequential gaps. Discuss motivation, main claim, comparisons, explanatory background and transitions. Keep observation, hypothesis, interpretation and proposal distinct.
4. Show a concrete slide-by-slide storyline: stable ID, role, title, message, evidence, visual plan, closing line (the one takeaway sentence that ends the slide and hands off to the next) and transition; the first slide names the target and objective. Title and closing-line register follow `references/message-style.md` (title = the slide's point as a noun phrase, closing line = one lesson or one number, jargon glossed at first use, no section-label prefixes such as "결과 1:"; user feedback 2026-10-31). Discuss and revise with the user. Run a content-budget check on that table before asking for approval: a slide that must carry more than one claim, more than three numbers beside its figure, or two unrelated topics (e.g. a library-composition chart plus reference-structure drawings) is flagged with a proposed split or a supplementary slide, and the user decides. Do not author the deck until the user accepts that flow. A topic exploration request or timeout is not approval. If this exact flow was already approved, continue without asking again. A request "same as before" (이전과 같이) carries the earlier approved flow from the presentation note; read it and proceed unless the user changes it.
5. Retain the approved flow, date and actual user task/turn reference in the presentation note. Read before `knowledge_revise`, use the current SHA and preserve prior context. Create a dedicated presentation note with `record_create` when none exists. Ordinary preparation-note writes are authorized; unrelated human research notes are not edit targets.

Example: “Project-A의 최근 실험 기록을 바탕으로 20분 연구 발표 흐름부터 같이 정하자. 핵심은 prior가 언제 도움이 되는지야.” After discussion: “이 흐름으로 확정하자. 슬라이드를 만들어 줘.”

## Brief-driven runs

When no Obsidian access or interactive approval is available (an automated build, a failed `obsidian_main`), an approved content brief stands in for the approval: record that in `storyline.json` (`approval.user_reference` = the brief) and skip Vault steps; never invent an approval timestamp beyond the brief's own date. Use `approval.basis = "brief"` when the brief has no date, write each slide's `visual` plan and `closing` line yourself (a brief supplies neither), and leave Obsidian paths out of the notes (use the brief's host-qualified source paths). PPTX-only details of such a run are in `references/pptx-production.md`.

## Build the HTML deck (after approval)

Materialize the approved flow as `storyline.json` (`references/storyline-format.md`; an HTML deck's storyline also carries `closing`, `glossary` and `owner`) and run `scripts/check_storyline.py` on that approved snapshot before the first build; separately verify that its approval reference is a real user decision. A goal loop later re-snapshots titles and closing lines into `work/storyline.json` while `work/storyline-v1.json` keeps the approved ids, roles and evidence, so the checker is not rerun on a loop's snapshot. Then:

1. **Scaffold** in the project's artifact location (`inbox/<talk>-deck/` or the project's slide folder), never inside this skill:
   `python3 scripts/new_deck.py /abs/<talk>-deck --title "…" --lang ko --slides title,figure,figure-render,closing`
   This copies the engine (`css/`, `js/`, `vendor/` with Pretendard and KaTeX) and writes `index.html` with the shape sprite inlined and the chosen fragments from `assets/deck/templates/` in order. For the Folio layout add `--theme folio` (fragments `cover,opener,plate,spread`) and draw with `scripts/folio_kit.py`; steps 2 and 5 to 8 are the same, and step 4's design reference is `references/folio.md`. Keep one slide per `<section class="slide">`; keep every sentence of the source in `<aside class="notes">`.
2. **Taste benchmark before the rest.** Build two or three representative slides first, including one mechanism scene, run the QA below, publish, and stop for the user's verdict. Only after the verdict build the remaining slides to that standard. This is how the reference deck was accepted (user decisions below). A handed-over deck that already passed this checkpoint, a headless builder run and a revision skip it.
3. **If you are a GPT model (Astra, Sol, Terra and so on), read `references/builder-notes-gpt.md` before drawing and follow it:** you copy worked slides from `scripts/kit_gallery.py` and draw with `scripts/scene_kit.py`, and `scripts/style_gap.py` measures how far the result is from the accepted decks. Claude models skip this step.
4. **Per slide**, read `references/design-system.md` once per thread and then: write the one message; decide what the single picture must show (actors, states, the change, in 2–3 cells); choose a layout fragment; draw the scene with the sprite shapes (`<use href="#shBlob">` etc.) and the scene grammar; put the source sentences and figure provenance in the notes. Structural evidence (PDB renders) follows `references/molecular-visualization.md`; a render sits in its own panel with leader labels, never as a decorative background.
5. **Render loop is yours, not the user's.** After each slide: `scripts/check_layout.py` (measured boxes: text outside its panel, label collisions, rim crossings, empty bands) and `scripts/shots.sh`, open the full-resolution PNG, fix overlaps and clipped labels, render again. A slide is "drawn" only after both pass: zero layout errors, no underfilled or unbalanced panel, and one full-size inspection with no finding. The first draft already follows the rules; the loop catches geometry, not taste.
6. **QA and delivery** per `references/qa.md`: `scripts/check_deck.py` (grid, closing line, citation markers, Korean endings, text sizes), `scripts/check_layout.py` (rendered measurement), `scripts/banned_copy_lint.py` (banned copy patterns, zero errors), `scripts/regression_run.py` (replays every recorded user-reported defect, zero FAIL; read its MANUAL lines during the inspection pass), all-slide PNGs plus the contact sheet, `scripts/export_pdf.sh` followed by `scripts/pdf_compare.py` (two PDF renderers, no flagged page), publish through the host's HTML preview workflow (host-context), verify served bytes, assets and the PDF, then report what was verified and what was not. The gates below (fact-check list, completion list) come before the delivery. Deliver the HTTPS link first, the local link, the PDF path and the folder on the host where it exists.
7. **Revisions** edit the slide in place; re-run `check_deck.py` and the shots for the touched slides; never regenerate the deck from an older spec over user edits. The publisher never overwrites a slug: publish `-v2`, `-v3`, … and say which is current.
8. **Obsidian archive** follows `references/workflow.md`: save the PDF and Markdown script in `Slides/` with date/title names, preserve the existing script length, and connect them through the presentation note. HTML preview slugs may retain internal version labels; archived filenames do not. When asked to export existing `<aside class="notes">` content, preserve every slide's notes in order without expanding the script.

## Design system (summary; details in `references/design-system.md`)

- Stage 1920×1080; title block starts at x 130 and ends at y 152; panels from y 176 to 898; every gutter 24 px; panel padding 20 px, so what a panel holds starts at x 130 under the title; the closing line is a white card at x 130–1790, y 922–1000; cite at the bottom, 17 px.
- Stage first (2026-11-02): key figures sit directly on the warm stage and panels are transparent. White is a card that holds one thing: one formula, one chart among several, the closing line. Panels in one row share a height. No coloured bars, blurred washes, gradient text, letter-spaced labels, icons or animation.
- Context-dependent academic terms stay in English in Latin script, on labels as well (`message-style.md` rule 4). Text budget: title (noun phrase), labels on the drawing, one closing line; sentences go to the notes. Type scale: 24 px is the base; body lines and figure labels 22–24 px, lane headers 24, emphasis 26–28, chart value labels 24–26, names 24–30; under 22 px only for muted reference notes or one dense 30-row chart (19 px) (type scale in `references/design-system.md`).
- Scene grammar: organic protein blobs with soft shading, capsule = small molecule, beads = ubiquitin, barrel = proteasome, cell with nucleus and DNA; the same actor keeps its shape across states; dashed outline = absent, red × = blocked, red dot = mutation; grays for machinery, one blue for the drug or path of interest, amber for the substrate, red only for a key phrase. Mechanism slides show the biological consequence (e.g. transcription → growth) as a cell-level panel, not only the molecular steps.
- Korean copy on slides is noun phrases (`references/korean-slide-copy.md`); citations `[n]` at the point of use and resolved in the cite line; every number and claim traces to a source in the notes.
- Taste standard: the accepted three-slide sample `taste-sample-20261030-v4` (Mac mini `inbox/html-deck-conversion-20261030/out/taste-sample/`); compare new work against it.
- The closing slide's question panel is the user's slot (`owner: user` in `storyline.json`): generate only a content header and two or three questions, never a header such as "발표자 생각", and goal-loop builders leave that slide alone.
- A deck with a cover figure places `kit.hero_bridge` on a transparent panel (gallery slide 1).
- Adopted on 2026-11-12 (details in `references/design-system.md`, Additions): a text-only section tracker in the kicker row (`init(deck, sections=…)`); the paper's equation number on a formula card (`fx(..., eq=)`, checked against the paper); four result tiles beside the question slot on the closing slide (`tile()`: one figure, one number, one phrase, the sentences in the notes); backup slides after the closing slide (`slide(..., backup=True)`, numbered B1) with the full table as `table()`; two or three builds on a dense mechanism (`step()`, `at()`), the last build being the whole slide; presenter keys L (laser), Z (zoom), T (tracker). No QR code on the cover.
- In `.fx` and `tex()` strings write `<` and `>` as `&lt;` and `&gt;` only when the string is not escaped again (a card path escapes once); otherwise KaTeX receives `&` and the formula shows a raw entity, which `check_layout.py` reports as `tex-unrendered`.

## Gates before delivery (both routes)

- Fact-check gate before delivery: extract every number, named comparison, citation and claim from the slides into a checklist, map each to its source (paper section, figure, record, data file), and mark unresolved items. The deck is not ready while any item is unresolved; say so in the first line of the delivery. Format checks (fonts, Korean endings, layout) never count as content verification.
- Completion list: each requested slide or change is reported as done or blocked; unfinished work is named as blocked, never offered as a "follow-up suggestion". A rebuild request ("skill 업데이트해서 다시 만들어") means a fresh build from the storyline, not a patch of the old deck; a figure that could not be fetched is reported, not silently kept.
- Content: existing evidence only; no new experiments or analyses designed for a talk unless asked. No pasted images of text or charts, no generated-image biology, house theme, no AI-template headers or callout boxes; on the PPTX route, editable native objects only. Rebuild charts and tables only from actual data, preserving units, subsets, conditions and uncertainty; mark missing inputs specifically; never manufacture results; example-deck numbers are not evidence for unrelated talks.
- Definitions on first use: Every metric, comparison or background set and every ambiguous abbreviation is defined on the slide where it first appears (a short label plus a one-line definition in the takeaway or a footnote). On the PPTX route `scripts/pptx/check_slide_conventions.py` findings about undefined terms block delivery; on the HTML route the same rule is `references/message-style.md` (jargon glossed at first use) and the storyline `glossary`.
- Citations: map each external claim, named compound and reused panel to its source at the point of use and number references from [1] by first appearance (`references/citations.md`); a footer bibliography alone is insufficient, and this study's own results carry no reference.
- Per-talk feedback list: keep the user's slide-level corrections in the presentation note and in `storyline.json`, and carry them into every fresh-context brief; rules kept only as prose regressed, rules turned into script checks held.
- Visual claims (centred labels, no overlaps) are proven on the rendered PDF or PNG, not on XML or the DOM source; if PowerPoint or Keynote rendering is blocked, report it once with the unblock step and name the renderer actually used.
- Deck numbering follows the application's slide numbers, not PDF pages.
- Existing-deck edits: for a PPTX, pull in the deck's own source template and the user's style reference first; when the user rejects a visual's style, keep the tool and change the style; never generated images for proteins, molecules, cells or data; each non-gray colour has one declared meaning for the whole deck; titles are topic or method noun phrases and findings go in the takeaway line; the presenter's own analyses carry no citation label.
- Fan-out for slide work: each subagent gets one output path, a required artifact list and a limit in wait calls; poll with the agent wait tool, not sleep; after two empty waits ask the agent for its blocker. Browser tasks are created from the GUI, not the API.

## Verification mode

Use normal visual review by default, including the inspection pass in `references/qa.md` (PPTX: the connection and legend pass in `references/pptx-qa.md`). When the user requests a rushed draft, or an agreed deadline requires it, skip full rendering and visual QA instead of spending the deadline on those checks. Preserve source fidelity and export the requested artifact; label the result as a draft with visual verification skipped. State which checks actually ran. This fast mode overrides the full-render requirements above for that delivery; do not claim visual quality or a verification pass that was not checked.

## Revisions (never lose user edits)

Use the latest user-edited deck as the source, not the original builder or an older generated copy. Check its current hash against the captured input and import it for focused changes. Do not regenerate the whole deck from an old storyline. Preserve untouched slides, notes and user layout changes. An exact user-requested revision authorizes that revision. Discuss agent-proposed substantive departures from approved messages/order; fit repairs need no new checkpoint.

Update the same presentation note with exact output paths, version, approved slide mapping and remaining needs. If recording fails, keep local work and the bridge outbox, report pending status, and never write Vault files directly.

When saving slides and scripts in Obsidian, follow `references/workflow.md` → “Archive slides and scripts in Obsidian”: PDF and Markdown under `Slides/` using date and title, no version/hash suffix, existing script length preserved, and reciprocal note links. Internal build versions remain in preparation history.

For an HTML deck this means editing the slide in place (Build step 7), and publishing a new slug rather than overwriting one.

## Copy and scores

- "이건 지금 이번에 한거처럼 규칙을 정해두면 요청하는거 그대로 만들 수 있는거아닌가?" and "좋은거같애. 1 2b 가 좋을듯?" → the rules live here so a request yields the deck directly; the taste benchmark of 2–3 slides stays as the one user checkpoint before the full build.
- Read `references/message-style.md` before writing visible copy (kickers, titles, lane headers, labels, closing lines, cite lines); a title must carry the slide's point.
- Count copy length by width: in the title limit (34), the kicker limits (section at most 14, subtopic at most 24) and the closing-line limit (12 to 48), a Latin letter or digit counts as 0.6 of a Hangul glyph, because English is narrower at the same size (rubric-message M1 to M3).
- A deck passes the goal when the message score and the design score are each at least 90, both scored by fresh judges.
- Visible copy (kickers, titles, lane headers, labels, body text, closing lines) contains none of the tokens `저자`, `발표자`, `모식`, `번역`; attribution and caveats go in the cite line (rubric-message M10).
- Use one written form per quantity across the deck, taken from the `glossary` in the storyline (a `use` form and `avoid` forms per quantity; the caller owns it); rubric-message M4(b) counts the `avoid` forms.
- A slide with `owner: user` is still read by the message judge. When the judge evidence names such a slide, the caller fixes the factual wording, records before and after, and runs `score_message.py` as well as `check_layout.py`.
- A design pass near 90 on one judge draw gets two replicate draws before it is reported.
- Judged loops (`goal_loop.py`, `goal_chain.py`, `iterate_deck.py`, `iterate_message.py`), judge variance and replicate draws, builders or judges on another CLI (`agent_cli.py`) and the equivalence test (`equiv_run.py`) are described with their measured results in `references/loops-and-builders.md`; read it before running any of them. They are calibrated on the research theme and are not run on a Folio deck. What they established: keep the judge fixed (Opus 5.5 max) when builders differ; start a loop with `--judges 3` and treat a single-draw pass near the threshold as provisional; when a judge finding recurs, change the rule instead of appending another prescription; on a GPT builder (Astra high, Sol xhigh) budget for the loop rather than expecting the first build to carry it, and move what a builder lost into a script check or a brief rule, not model-specific prose; where Opus 5.5 is stopped by the safety classifier, Sonnet 5.5 is the Claude baseline and no separate paper is run for an Opus 5.5 baseline.

## Hosts

- Rendering needs Chrome (`CHROME` env; default `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`). No npm, no Python packages.
- Publishing: the Mac mini `html-preview` publisher (path and URL form in `~/.codex/host-context.md`) prints the MacBook HTTPS link first, then the Mac mini local link; verify both routes as in `references/qa.md`. On a host without a publisher, deliver the deck folder and the PDF and say so.
- The engine copy in `assets/deck/` is canonical; the inbox starter `html-deck-starter-20261030` on the Mac mini holds the development history and the example decks.
- PPTX route hosts and tools: `references/pptx-production.md`.

## Fresh-context rebuild and skill evaluation

When the user explicitly asks to rebuild from a fresh context, use the approved content brief and raw evidence with the clean template, not the previous deck or its builder. This is a new build, not a revision of the old layout. Preserve the old outputs. For an explicitly requested fresh-context skill evaluation, follow `references/fresh-context-evaluation.md`; assess the independently produced artifact before changing the skill based on observed failures.

## Maintenance

A new shape that will recur goes into `assets/deck/sprite-research.svg`; an accepted style correction becomes a `check_deck.py` rule or a line in `references/qa.md` in the same turn (PPTX route: a check under `scripts/pptx/` or a line in `references/pptx-qa.md`); every visual defect the user reports also becomes one case in `regression/manifest.json` in that turn (`regression/README.md`); an entry in User decisions is never dropped or narrowed without asking. The fresh-context brief carries the approved storyline file and the full feedback ledger, never a summary. Validate with the system skill-creator's `quick_validate.py` (`uv run --with pyyaml`), never by installing validator dependencies into a talk's environment; after touching the PPTX kit run `scripts/pptx/test_*.py` and `scripts/test_storyline_brief.py` with the runtime Python, and after touching a checker or the theme run `scripts/regression_run.py`; after touching `scene_kit.py` or `folio_kit.py`, a theme stylesheet or a checker, rebuild the matching gallery (`kit_gallery.py`, `folio_gallery.py`) in a scratch deck, run `check_deck.py` and `check_layout.py` on it, and refresh the renders in `assets/kit-gallery/` or `assets/folio-gallery/` that changed.
